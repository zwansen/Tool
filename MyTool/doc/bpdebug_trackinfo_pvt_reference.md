# BPDEBUG 二进制数据解析结果 · 逐字段通俗字典（ProtocolDecoder.dll + bpdebug_track_dump.exe）

> **这份文档讲什么**：BPDEBUG 日志里**二进制部分**（CavBin 帧）经
> `ProtocolDecoder.dll` + `bpdebug_track_dump.exe` 解析后，**能拿到什么数据、结构长什么样、
> 每个字段是什么意思**——用大白话讲，逐字段给表格。
>
> **先分清两件事**（很多人会混）：
> - **ASCII 文本部分** = BPDEBUG 日志里可见的 `$C*` / `$CH*` 语句（逗号分隔文本，
>   模组 debug_print 输出）。逐字段字典见 **`doc/BPDEBUG解析协议.md`**。
> - **二进制部分** = 同一日志里的 CavBin 二进制帧（0xC7 0xE5 同步头，含 TrackInfo /
>   PVT / RawObs / EOE 等消息）。肉眼读不了，必须靠解码器。**本文档讲的就是这一部分**。
>
> **数据从哪来**：`bpdebug_track_dump.exe`（链接 `ProtocolDecoder.dll`）把二进制帧里的
> TrackInfo / PVT 消息解析出来，按"冷启动循环（Reset）"重新组织，输出一份 JSON
> （`*.track.json`），再被 TTFF 搜星报告拿来画图。
>
> **权威性标注**
> - ✅ **实取**：全部字段来自本仓库真实解析流程（`ttff_chobs_acq_report.py` / `acq_report.js`），
>   并已用真实样本 `LG690P_tongxian_1.log`（1.19GB）的解析结果逐字段核对（样本数值写在每张表里）。
> - ⚠️ 底层 bit 含义（`sat_state`/`pvt_state` 各位的语义）来自 ProtocolDecoder 内部约定，
>   本仓库按消费方使用的掩码标注（与 workbench 跟踪视图同源）。

## 1. 一句话看懂

```
BPDEBUG 日志（1.19GB 示例）
 ├─ 二进制帧部分 ── DLL 解析 ──► 每个"冷启动循环"给出：
 │                              ├─ 星历有效颗数随时间变化（秒级曲线）
 │                              ├─ 参与解算颗数随时间变化（秒级曲线）
 │                              ├─ 可参与位置解信号数随时间变化（按频点）
 │                              └─ 每颗星什么时候开始被跟踪 / 星历有效 / 参与解算
 └─ ASCII 文本部分 ──► 见 BPDEBUG解析协议.md（$C* 语句）
```

- **冷启动循环（Reset）**：日志里每次出现冷启动复位码（如 `13F`）算一次循环。
  样本 `LG690P_tongxian_1` 共 **63 次**冷启动。
- **时间轴**：一律用"相对 Reset 秒"（复位那一刻 = 0 秒），采样 **10Hz**（每 0.1 秒一个点）。
- **曲线数组**：`第 i 个点 = 复位后第 i×0.1 秒的值`。例如 1852 个点 ≈ 185.2 秒。

## 2. 解析结果整体结构（JSON）

```json
{
  "version": "1.0.0",          // 导出格式版本
  "source": "ProtocolDecoder.dll",
  "input": "…\\LG690P_tongxian_1.log",
  "sample_hz": 10,             // 采样率：每秒 10 个点
  "time_axis": "seconds_from_reset",
  "n_cycles": 63,              // 共 63 次冷启动
  "track_frames": 13677,       // 二进制里解析出的 TrackInfo 帧总数
  "eoe_frames": 116126,        // 解析出的 EOE 帧总数
  "eph_mask": "0x20000000",    // "星历有效"用 sat_state 的第 29 位判断
  "fix_mask": "0x08000000",    // "参与解算"用 sat_state 的第 27 位判断
  "pvt_mask": "0x80000000",    // "可参与位置解"用 pvt_state 的第 31 位判断
  "cycles": [ … 63 个循环，每个的结构见第 3 节 … ]
}
```

## 3. 每个冷启动循环里有什么（cycle 字典）

```json
{
  "reset_n": 301,          // 第几次冷启动（排序号，用来和其它分析结果对齐）
  "reset_code": "13F",     // 复位码后缀
  "duration_s": 185.1,     // 这次循环持续多少秒
  "n_epochs": 1852,        // 共多少个采样点（= duration_s × 10）
  "freqs": [15个频点],      // 这次循环出现过的频点，如 B1C/B1I/B2a/B2b/E1…
  "eph_total_curve": […],  // 每秒"星历有效"的卫星颗数
  "fix_total_curve": […],  // 每秒"参与解算"的卫星颗数
  "pvt_total_curve": […],  // 每秒"可参与位置解"的信号个数（按信号算，会比卫星多）
  "eph_prns": […],         // 每秒"星历有效"的是哪几颗星（PRN 列表）
  "fix_prns": […],         // 每秒"参与解算"的是哪几颗星
  "pvt_freq_curves": {},   // 每个频点的"可参与位置解"曲线（如 B2b: […颗/秒…]）
  "pvt_freq_prns": {},     // 每个频点每秒是哪些 PRN
  "sats": [ … 每颗星的详情，见第 4 节 … ]
}
```

### 逐字段含义表（cycle）

| 字段 | 类型 | 白话解释 | 样本值 |
|------|------|---------|--------|
| `reset_n` | 整数 | 冷启动循环序号（第 N 次复位） | `301` |
| `reset_code` | 文本 | 复位的冷启动码后缀 | `13F` |
| `duration_s` | 小数 | 这次循环从复位到结束共多少秒 | `185.1` |
| `n_epochs` | 整数 | 采样点数 = duration_s × sample_hz | `1852` |
| `freqs` | 数组 | 本循环用到的所有频点 ID | 15 个（B1C…QZL5） |
| `eph_total_curve` | 整数数组 | **每秒"星历有效"的颗数**——星历已就绪、可参与解算候选的卫星数 | 非零 1799/1852 |
| `fix_total_curve` | 整数数组 | **每秒"参与解算"的颗数**——真正在参与定位解算的卫星数 | 非零 1799/1852 |
| `pvt_total_curve` | 整数数组 | **每秒"可参与位置解"的信号数**（信号级，同星多频点会重复计） | — |
| `eph_prns` | 数组的数组 | 每个采样点，星历有效的是哪几颗星（PRN） | `[]` / `[24,33,…]` |
| `fix_prns` | 数组的数组 | 每个采样点，参与解算的是哪几颗星 | — |
| `pvt_freq_curves` | 字典 | 按频点拆分的可参与位置解曲线，如 `"B2b": [0,0,2,2,…]` | — |
| `pvt_freq_prns` | 字典 | 按频点拆分的 PRN 列表（图例/悬停用） | — |
| `sats` | 数组 | 本循环出现过的所有卫星（见下） | 92 颗 |

> **为什么星历有效 ≠ 参与解算？** 星历有效 = 这颗星"能用"（星历已下载）；
> 参与解算 = 这颗星"正在被用来算位置"。仰角低、信号差、被剔出的星可能星历有效但不参与解算。

## 4. 每颗星的详情（sats 字典）

```json
{
  "id": "BDS-1",             // 系统-编号
  "sys": "BDS",              // 卫星系统
  "prn": 1,                  // PRN 号
  "freqs": ["B1I","B2b"],    // 这颗星用了哪些频点
  "track_spans": [[17.3, 185.1]],  // 什么时候开始被跟踪 → 什么时候结束
  "eph_spans":  [[47.2, 185.1]],   // 什么时候星历有效
  "fix_spans":  [[47.2, 185.1]],   // 什么时候参与解算
  "first_eph_s": 47.2,       // 首次星历有效时刻（秒）
  "first_fix_s": 47.2        // 首次参与解算时刻（秒）
}
```

| 字段 | 类型 | 白话解释 |
|------|------|---------|
| `id` | 文本 | 卫星唯一标识，如 `BDS-1`、`GPS-10`、`GAL-4` |
| `sys` | 文本 | 系统：BDS(北斗)/GPS/GAL(伽利略)/GLS(格洛纳斯)/QZSS/IRNSS/SBAS |
| `prn` | 整数 | 同系统内的 PRN 编号 |
| `freqs` | 数组 | 该星用到的频点（BDS-1 只有 B1I+B2b，GPS-10 有 L1+L2+L5） |
| `track_spans` | 区间数组 | 跟踪时间段 `[[开始秒, 结束秒]]`（可能多段） |
| `eph_spans` | 区间数组 | 星历有效时间段 |
| `fix_spans` | 区间数组 | 参与解算时间段 |
| `first_eph_s` | 小数/null | 第一次星历有效的时刻；一直没星历则为 `null` |
| `first_fix_s` | 小数/null | 第一次参与解算的时刻；一直没参与则为 `null` |

> 从样本能看出的典型现象：
> - **跟踪最早**：BDS-1 复位后 17.3s 就被跟踪，47.2s 才星历有效——"先看到星，后拿到星历"。
> - **星历有效但从不参与解算**：如 `GAL-19`（eph 有、fix_spans 空、first_fix_s=null）、`GPS-2`、`QZSS-7`。
> - **几乎看不到但一直有跟踪**：`GPS-17` 只跟踪了 1 秒（153.2→154.2）就消失。

## 5. 状态位是什么意思（sat_state / pvt_state）

DLL 对每颗星/每个信号维护一个 32 位状态字，本工具只看 3 个位：

| 位 | 掩码 | 判断对象 | 含义（白话） | 粒度 |
|----|------|---------|-------------|------|
| bit 29 | `0x20000000` | `sat_state` | **星历有效**：这颗星的星历已可用，能进解算候选 | 按星 |
| bit 27 | `0x08000000` | `sat_state` | **参与解算**：这颗星此刻真的在参与定位解算 | 按星 |
| bit 31 | `0x80000000` | `pvt_state` | **可参与位置解**：这个信号满足解算条件（≠实际参与） | 按信号 |

**按星 vs 按信号**：一颗星可能同时播 B1I/B2b 两个频点——按星统计只算 1 颗，
按信号统计算 2 个。所以 `pvt_total_curve` 数值会 ≥ `fix_total_curve`。

## 6. 这些数据最后画成报告里的哪些图

| 报告卡片 | 用到的字段 |
|----------|-----------|
| 星历有效 / 参与解算 颗数 vs 时间 | `eph_total_curve`（虚线）/ `fix_total_curve`（实线） |
| 按星时间轴 · 星历有效 / 参与解算 | 每颗星的 `track_spans`/`eph_spans`/`fix_spans` 色带 |
| 可参与位置解算 vs 时间（信号级） | `pvt_total_curve` + `pvt_freq_curves` |
| RawObs 在视星数 vs 时间 | 不属于 DLL 解析（来自帧解析），跳过 PVT 时仍会出 |

> 勾选「跳过 PVT/星历曲线」时 DLL 不运行，`eph/fix/pvt` 全部为空，
> 上面前三类图就没有数据（RawObs 图不受影响）。

## 7. 解析结果文件在哪

- 缓存：`<日志所在目录>/_track_dump_cache/<日志名>.full.v2.track.json`
- 报告数据：`output/ttff_merged/bpdebug/report_data.full.json`（report_data.js 是它的精简版）
- 同一个文件只解析一次，之后秒出（缓存复用）。

**一句话总结**：DLL 把 BPDEBUG 二进制帧变成"每颗星每个时刻的星历/解算状态"，
再汇总成"每秒星历有效/参与解算/可参与位置解的颗数曲线"和"每颗星的时间段"——
报告里那几张图，画的就是这些数据。
