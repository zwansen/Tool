# ARMv7-A/R 芯片异常原因排查手册（白话版）

> 来源：`DDI0406C_d_armv7ar_arm.pdf` 第 **B1.9 Exception descriptions** 章（PDF 页 B1-1204 ~ B1-1224）。  
> 目标：把芯片手册里的异常描述“翻译”成工程师能直接对照排查的语言。

---

## 前言：异常是什么？

可以把 ARM 芯片想象成一个一直在按顺序“读指令、执行、读写数据”的工人。当这个工人在某个环节遇到**它处理不了、不该执行、或者外部打断它**的情况时，就会触发一次“异常”。异常一旦发生，CPU 会停下当前工作，跳到一个固定的“异常处理入口”（向量表），由软件去处理。

对于产品调试来说，异常的最终表现通常是：

- 死机、重启、卡死
- 串口打印出 `Data abort`、`Prefetch abort`、`Undefined instruction` 等字样
- 调试器看到 PC 跑到了异常向量表地址（如 `0x00000004`、`0x0000000C` 等）
- 某些功能调用后系统直接崩溃

本文档把每一种异常用“**是什么 → 为什么会发生 → 现场怎么看 → 怎么排查**”四个维度讲清楚。

## 一、异常总览表

| 异常名 | 一句话解释 | 最常见的现场现象 | 通常谁惹的祸 |
|---|---|---|---|
| **Reset** | 芯片复位，重新开始跑 | 系统重启、启动代码重新执行、看门狗复位 | 上电、复位引脚、看门狗、软复位 |
| **Undefined Instruction** | CPU 读到一条它不认识的指令 | 打印 `Undefined instruction`，PC 指向某条指令 | 跑飞了、执行到数据区、协处理器没开、除零、浮点指令未使能 |
| **Hyp Trap** | 普通世界的指令被 Hypervisor 截获 | 虚拟化场景下 Guest OS 执行特权指令 | 虚拟化配置、HCR/HCPTR 等寄存器捕获位 |
| **SVC** | 用户程序调用操作系统服务 | 系统调用 `SVC #0` 后进入内核态 | 正常系统调用，不是错误 |
| **SMC** | 普通世界调用安全世界（TrustZone） | 执行 `SMC` 指令后进入 Monitor 模式 | TrustZone 相关调用 |
| **HVC** | 客户机调用 Hypervisor | 虚拟化下 Guest 调用 Hypervisor 服务 | 正常虚拟化调用，不是错误 |
| **Prefetch Abort** | 取指令时内存访问失败 | 打印 `Prefetch abort`，PC 指向无效地址 | 代码跑飞、PC 指向未映射内存、Flash 损坏、调试断点/BKPT |
| **Data Abort** | 读写数据时内存访问失败 | 打印 `Data abort`、LR 指向一条访存指令 | 访问空指针、越界数组、未映射外设、内存保护违规 |
| **Virtual Abort** | 虚拟化下的异步异常被虚拟化转发 | 虚拟化场景中 Guest 收到异步 abort | HCR 配置、虚拟中断路由 |
| **IRQ** | 普通外部中断 | 定时器、串口、GPIO 等外设打断 CPU | 正常中断处理，不是错误 |
| **Virtual IRQ** | 虚拟化下的虚拟中断 | Guest OS 收到虚拟定时器/虚拟外设中断 | 虚拟化中断注入 |
| **FIQ** | 快速外部中断 | 高优先级中断打断 CPU | 正常快速中断，不是错误 |
| **Virtual FIQ** | 虚拟化下的虚拟快速中断 | Guest OS 收到虚拟 FIQ | 虚拟化中断注入 |

> **先记住两个最重要的“错误类异常”**：`Undefined Instruction`、`Data Abort`、`Prefetch Abort`。产品现场 90% 以上的异常死机都是这三个。

## 二、错误类异常详解（重点看）

### 2.1 Undefined Instruction（未定义指令异常）

#### 是什么？
CPU 解码一条指令时，发现这条指令它不认识，或者这条指令在当前状态下不被允许执行。

#### 实际现象
- 串口或调试器打印：`Undefined instruction`
- LR（链接寄存器）指向触发异常的那条指令地址
- 可能出现在刚调用某个新功能、打开某个新驱动之后

#### 常见原因

| 原因 | 现场表现 | 排查方法 |
|---|---|---|
| **CPU 跑飞了，取到了数据区/垃圾数据** | PC 指向一个奇怪的地址，比如堆、栈、或外设区 | 查看 LR 和 PC，确认是否在代码段；检查是否数组越界、函数指针被改写 |
| **协处理器没开，但代码用了协处理器指令** | 使用了 VFP/NEON/CP15 等指令但 `CPACR` 未使能 | 检查 `CPACR` 等访问控制寄存器；确认是否没初始化浮点单元 |
| **Security Extensions 限制** | 非安全世界试图访问安全世界资源 | 检查 `NSACR`；确认指令是否只能在安全态执行 |
| **Virtualization Extensions 限制** | Guest OS 里执行了被 Hypervisor 禁止的协处理器指令 | 检查 `HCPTR` 等捕获配置 |
| **浮点异常被捕获** | 浮点运算出错且相关异常使能 | 检查浮点控制寄存器、FPEXC |
| **ARMv7-R 中 SDIV/UDIV 除零** | 执行整数除法时除数为 0 且 `SCTLR.DZ=1` | 检查触发指令附近的除法运算；ARMv7-A 通常除零返回 0，不会异常 |
| **Thumb/ARM 状态错配** | 在 Thumb 状态下跳到了 ARM 指令，或反之 | 检查跳转地址最低位、LR 的 bit0、BX/BLX 用法 |

#### 排查口诀
> **先看 LR 指向哪里 → 再看那条指令是什么 → 最后看协处理器/状态位/权限有没有开。**

---

### 2.2 Prefetch Abort（预取指异常）

#### 是什么？
CPU 去拿下一条要执行的指令时，发现这条指令所在的内存读不出来，或者不允许执行。

> 注意：这是**取指令阶段**出错的异常，不是读写数据阶段。

#### 实际现象
- 串口或调试器打印：`Prefetch abort`
- PC 指向的地址无法取指
-  often 伴随着 LR 指向某个无效地址

#### 常见原因

| 原因 | 现场表现 | 排查方法 |
|---|---|---|
| **PC 跑飞了** | LR 指向未映射区域、RAM 以外、或已被破坏的地址 | 查看 LR、栈回溯；找最近的函数跳转/返回 |
| **函数返回地址被破坏** | 栈溢出、数组越界覆盖了返回地址 | 检查栈深度、局部数组大小、递归深度 |
| **代码段被意外改写** | Flash/EEPROM 里的代码被破坏 | 校验代码段 CRC；检查是否有 DMA 越界写内存 |
| **MMU/MPU 没有映射代码区** | 新加的代码段、动态加载的代码没有映射 | 检查页表/MPU 区域配置；确认地址是否在有效映射内 |
| **指令放在不可执行的内存** | 比如在某些安全芯片上，数据区被标记为 XN（Execute Never） | 检查内存属性；确认是否把数据当代码执行 |
| **调试断点/BKPT** | 调试器下了软件断点或代码里写了 `BKPT` 指令 | 检查是否有断点残留；搜索代码里的 `BKPT` |
| **Breakpoint/Vector catch 调试事件** | 调试配置触发 | 检查调试寄存器、DBGBCR、DBGVCR |

#### 排查口诀
> **Prefecth Abort = PC 指错地方了。重点查 PC 怎么跑到错误地址的：函数返回、跳转、栈破坏、MMU/MPU 映射。**

---

### 2.3 Data Abort（数据中止异常）

#### 是什么？
CPU 执行一条读/写内存的指令时，发现访问的内存读不出来或不允许访问。

#### 实际现象
- 串口或调试器打印：`Data abort`
- 通常 LR 减去 8 就是那条触发异常的访存指令
- 如果开启了 MMU，可能还伴随 `DFSR`、`DFAR` 等寄存器有值，能直接指出出错的虚拟地址

#### 常见原因

| 原因 | 现场表现 | 排查方法 |
|---|---|---|
| **访问空指针/野指针** | 地址是 0x00000000 或很小的值 | 查看触发指令的源寄存器/基址寄存器 |
| **数组越界、缓冲区溢出** | 地址计算后跑到不该去的地方 | 查看基址寄存器和偏移量；检查数组下标 |
| **访问未映射的外设地址** | 新加外设没开时钟、没配 MMU/MPU | 确认外设基地址、时钟使能、内存映射表 |
| **访问已释放的内存** | 堆内存被释放后继续使用 | 检查内存管理、指针生命周期 |
| **对齐错误** | 访问地址没有按数据宽度对齐 | 查看地址是否为 4 字节/8 字节对齐 |
| **权限错误（MMU/MPU）** | 用户态访问内核态区域、只读区被写 | 查看 `DFSR` 的 status 位；检查页表/MPU 权限 |
| **Watchpoint 调试事件** | 调试器设置了数据观察点 | 检查调试配置 |
| **异步外部 abort** | 总线错误、DRAM 出错、AXI 总线返回错误 | 检查总线状态、DRAM 控制器日志 |

#### 排查口诀
> **Data Abort = 访问了不该访问的内存。重点查地址来源、MMU/MPU 映射、权限、对齐。**

#### 实用技巧
- **MMU 系统**：立刻读 `DFAR`（Data Fault Address Register）和 `DFSR`（Data Fault Status Register），它们能直接给出出错的虚拟地址和原因码。
- **无 MMU 系统**：直接看触发指令的基址寄存器，算出来的地址就是物理地址。

## 三、非错误类异常详解（多为正常机制）

### 3.1 Reset（复位）

#### 是什么？
芯片被复位，从头开始跑启动代码。

#### 实际现象
- 系统突然重启
- PC 回到复位向量（0x00000000 或 0xFFFF0000）
- 所有寄存器被重置

#### 常见原因
- 上电复位
- 外部复位引脚被拉低
- 看门狗超时复位
- 软件主动复位（写复位寄存器）
- 电源跌落/Brown-out 复位

#### 排查方向
> **看复位源寄存器**。大多数 SoC 都有记录复位原因的寄存器（如 `RST_SR`、`RCM` 等），能告诉你是看门狗、上电、还是软件复位。

---

### 3.2 SVC（Supervisor Call）

#### 是什么？
用户态程序通过 `SVC` 指令主动请求操作系统服务。

#### 实际现象
- 系统调用入口（如 `svc #0`）
- 进入 Supervisor 模式
- 这是**正常机制**，不是错误

#### 排查注意
如果 SVC 后死机，通常不是 SVC 本身的问题，而是：
- 系统调用号传错了
- 参数指针无效（进内核后触发 Data Abort）
- 中断/调度没配好

---

### 3.3 IRQ / FIQ（中断/快速中断）

#### 是什么？
外部设备通过中断线打断 CPU，让它先去处理外设事件。

#### 实际现象
- 定时器、串口、DMA、GPIO 等外设触发
- 进入 IRQ/FIQ 模式
- 处理完中断后返回原任务

#### 排查注意
如果进中断后死机：
- 中断服务函数里访问了非法地址（Data Abort）
- 中断嵌套过深导致栈溢出
- 中断向量表配错，跳到了空函数
- 高优先级中断一直来，低优先级任务饿死

---

### 3.4 SMC（Secure Monitor Call）

#### 是什么？
非安全世界通过 `SMC` 指令调用安全世界（TrustZone）的功能。

#### 实际现象
- 常见于安全启动、安全存储、DRM 等场景
- 进入 Monitor 模式

#### 排查注意
- SMC 参数/调用号错误可能导致安全世界返回错误码
- 如果 SMC 被 trap 到 Hyp 模式，说明 `HCR.TSC=1`，属于虚拟化配置问题

---

### 3.5 HVC / Hyp Trap / Virtual IRQ / Virtual FIQ / Virtual Abort

#### 是什么？
这些都是 **Virtualization Extensions（虚拟化扩展）** 相关的异常，只在跑 Hypervisor/虚拟机时出现。

#### 实际场景
- 虚拟机（Guest OS）执行特权指令 → 被 Hypervisor 捕获（Hyp Trap）
- Guest OS 需要 Hypervisor 服务 → 调用 `HVC`
- Hypervisor 给 Guest 注入虚拟中断 → Virtual IRQ/FIQ

#### 排查注意
如果你的产品**没有跑虚拟化**，可以忽略这些异常。  
如果跑了虚拟化，重点看 `HSR`（Hyp Syndrome Register）和 `HCR` 相关配置。

## 四、现场排查流程

拿到一个异常死机现场，推荐按下面步骤排查：

### 步骤 1：确认异常类型
看串口打印、调试器输出或 LR/PC 所在向量地址：

| 向量地址偏移 | 异常类型 |
|---|---|
| 0x00 | Reset |
| 0x04 | Undefined Instruction |
| 0x08 | SVC / SMC（入口相同，由指令区分） |
| 0x0C | Prefetch Abort |
| 0x10 | Data Abort / Virtual Abort |
| 0x14 | Hyp Trap（虚拟化） |
| 0x18 | IRQ / Virtual IRQ |
| 0x1C | FIQ / Virtual FIQ |

### 步骤 2：定位触发点
- **Undefined Instruction / Prefetch Abort**：LR 通常直接指向触发指令。
- **Data Abort**：LR 减去 8（ARM 状态）或减去 2/4（Thumb 状态）指向触发指令。
- **IRQ/FIQ**：LR 减去 4 指向被中断处。

### 步骤 3：看关键寄存器
- **MMU 系统**：`DFAR`/`DFSR`（Data Abort 时）、`IFAR`/`IFSR`（Prefetch Abort 时）。
- **异常模式寄存器**：`SPSR_xxx`、`LR_xxx`。
- **复位源寄存器**：判断是不是 Reset。
- **CPSR**：看当前模式、中断屏蔽位、Thumb/ARM 状态。

### 步骤 4：反查代码
- 把 LR/PC 对应的地址反汇编，看看到底是哪条指令。
- 检查这条指令附近的代码：有没有越界、有没有未初始化的指针、有没有访问新外设。

### 步骤 5：检查内存/映射/权限
- 地址是否在有效映射范围内？
- 权限是否允许读/写/执行？
- 是否对齐？

## 五、典型问题速查

### 问题 1：一跑某个新驱动就 Undefined Instruction
**可能原因**：
- 驱动里用了 VFP/NEON 浮点指令，但启动代码没开浮点单元（`CPACR` 没配）。
- 驱动被编译成了 Thumb-2，但当前 CPU 只支持 ARM。
- 驱动加载到了没有执行权限的内存。

### 问题 2：运行一段时间后死机，LR 指向栈里
**可能原因**：
- 栈溢出，返回地址被改写成非法值 → Prefetch Abort。
- 中断嵌套太深，_irq 栈溢出。

### 问题 3：访问某个外设就 Data Abort
**可能原因**：
- 外设时钟没开。
- 地址写错了（多看一个 0、少看一个 0）。
- MMU/MPU 里没映射这个区域。

### 问题 4：启动过程中反复 Reset
**可能原因**：
- 看门狗没喂。
- 启动代码访问了未映射内存触发 Data Abort，但异常向量也没配好，导致又进 Reset。
- 电源不稳定。

### 问题 5：系统调用后死机
**可能原因**：
- 系统调用号越界，跳到了非法地址。
- 系统调用参数是野指针，进内核后触发 Data Abort。

## 六、给不同读者的建议

### 如果你是应用/驱动工程师
重点关注：
- **Data Abort**：空指针、数组越界、未初始化的外设地址
- **Undefined Instruction**：协处理器没开、跑飞
- **Prefetch Abort**：函数返回地址被改、PC 跑飞

### 如果你是系统/启动工程师
重点关注：
- Reset 后的启动流程
- 异常向量表是否配置正确
- MMU/MPU 页表是否覆盖代码段和数据段
- 各协处理器（VFP/NEON/CP15）的使能

### 如果你是虚拟化/安全工程师
重点关注：
- HCR、HCPTR、HDCR、HSTR 捕获配置
- SCR 对 IRQ/FIQ/Abort 的路由
- TrustZone 切换时 NSACR、MVBAR、HVBAR 的配置

## 七、附录：异常入口后 CPU 做了什么？

异常发生后，硬件会自动做以下事：

1. **保存现场**：把当前 CPSR 存到 SPSR，把返回地址存到 LR（Hyp 模式存到 ELR_hyp）。
2. **切换模式**：根据异常类型进入对应模式（如 Abort、Undefined、IRQ 等）。
3. **关中断**：通常自动把 IRQ 关掉（`CPSR.I = 1`），有些异常还会关 FIQ 和异步 abort。
4. **清 IT 状态**：`CPSR.IT` 清零。
5. **设置指令集和大小端**：根据控制寄存器决定是 ARM 还是 Thumb、大端还是小端。
6. **跳转向量表**：PC = 异常基址 + 向量偏移。

软件需要在异常处理函数里：
- 保存更多寄存器（如果需要）。
- 分析异常原因（读 FAR/FSR 等）。
- 处理或记录异常。
- 恢复寄存器并返回（`SUBS PC, LR, #x` 或 `ERET`）。
